## Separate investigation: HR / personnel / comp process and the BambooHR API

Flagged as its own workstream. Scope and first findings:

**What BambooHR exposes.** BambooHR has a documented REST API (v1) authenticated with a per-user API key (generated by the user in their Bamboo account; the key inherits that user's access level). Relevant endpoints:

- Employee directory and employee fields (title, department, division, location, supervisor, hire date, status).
- Custom reports: a saved report in Bamboo can be pulled by id as CSV or JSON, which is the cleanest way to get a controlled column set.
- Tabular tables per employee: job information history, employment status history, compensation history. Compensation is permission-gated by the API user's access.
- Webhooks on field changes, which could push title or department changes to the warehouse without polling.
- Time off and benefits endpoints (not needed for this).

These points are from general knowledge of BambooHR's API and need to be confirmed against the current developer documentation and BB Living's plan tier before anything is built.

**What to decide.**

1. Who holds the API key, at what access level. Recommendation: a service user limited to directory, job information, and employment status. Keep compensation out of any automated pull until the warehouse has a restricted schema with row-level security.
2. Where the non-sensitive extract lands: a `hr` schema in BBLivingDW fed through BBL-DataSource `inputs/hr/` (titles, departments, supervisors, hire dates, status), refreshed nightly. This is what the org chart, the responsibility matrix, and the Critical Date Calendar owner labels should read from.
3. Where the sensitive extract lands: local or the restricted Personnel folder, pulled on demand, never through the shared pipeline.
4. What the canonical title and department list is (see discrepancies below). Bamboo should be corrected to match it, then become the source of truth; until then every report built on Bamboo inherits the errors.

**Process improvements to evaluate alongside the API.**

- Headcount and comp planning now happen in spreadsheets and the Compensation Planner artifact; Bamboo is updated afterward by hand. Reverse that: Bamboo first, planner reads from Bamboo.
- Quarterly KPI and review cycles (HR Manager's remit per the 2027 structure) have no system; Bamboo's performance module or a simple warehouse table could hold them.
- Onboarding checklists exist per role on SharePoint (2024) and reference Bamboo for the new-hire packet; they should be regenerated from the canonical title list.
